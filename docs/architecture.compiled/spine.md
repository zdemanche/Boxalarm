# Architecture Spine: Boxalarm — Architecture (Fire Department Operations Platform)

## Service Inventory & Boundaries

- **alerting-service** — dispatch ingress, exactly-once fan-out, per-member channel escalation (push+SMS parallel → voice), department-level tone ladder (F1.12-F1.14), mutual aid prompt, receipts, self-test, canary, alert audit log — isolated life-safety plane, own DynamoDB table, own SNS FIFO topic + SQS FIFO queues/DLQs. Wave 1.
- **platform-service** — Cognito triggers, department config (F9.3), Verified Permissions policy admin, cross-service audit log sink (F9.4), data export (F9.5) — DynamoDB (shared "platform-service" physical table). Wave 1.
- **personnel-service** — roster, quals, attendance, LOSAP points, availability, duty shifts, open-shift signup — logical service on the shared platform-service table. Wave 1.
- **apparatus-service** — apparatus registry, check sheets, defects, OOS tracking, maintenance, SCBA, testing schedules, compartments — shared platform-service table. Wave 2.
- **incident-service** — NERIS-native incident model, pre-population, guided completion, NERIS submission, submission status, search — own dedicated DynamoDB table. Wave 2.
- **training-service** — certifications, expiry alerting, drills, training hours, transcripts — shared platform-service table. Wave 3.
- **reporting-service** — chief dashboard, LOSAP/ISO/grant reports, response-time analytics, CSV/PDF export — no primary data of its own; queries purpose-built GSIs on the platform-service table (v1; OpenSearch deferred). Wave 3.
- **inspections-service** — occupancy, pre-incident plans, inspection/violation tracking, hydrants, map retrieval — shared platform-service table. Wave 4.
- **inventory-service** — equipment/PPE registry, consumable stock, asset lifecycle — shared platform-service table. Wave 4.
- **notification-service** — non-alert member/officer notification (cert expiry, defect routing, testing-due, PPE expiry, reorder thresholds, shift-coverage gaps); in-app inbox, digest batching, notification preferences — shared platform-service table, LOB failure domain, shares nothing with alerting. Wave 1.
- **web-spa** — React web SPA, single responsive app for officer/chief/training/apparatus/admin desk workflows (F8 dashboards, F9 config, NERIS report authoring, F5/F6 back-office). No MFE — one team, one release train.
- **mobile-app** — React Native app (iOS + Android, shared codebase), the life-safety alert delivery surface (Critical Alerts / full-screen intent), truck checks, schedule, self-service, offline-first local store + outbox sync.
- **infrastructure** — Pulumi IaC (`boxalarm-infrastructure` repo), all AWS resources for every environment, GitHub OIDC deploy, sole owner of Pulumi state; wires the 10 backend services to API Gateway, DynamoDB, EventBridge, SNS/SQS, Cognito, Verified Permissions.

**Physical vs. logical note:** 10 backend service *code* boundaries exist, but only **3 physical DynamoDB tables**: `alerting-service` (own table), `incident-service` (own table), and `platform-service` (shared by personnel, apparatus, training, reporting, inspections, inventory, notification, and platform-service itself). This is a deliberate, named deviation from the Moonaan one-table-per-service default, taken on cost-floor and shared-lifecycle grounds (Data Model §1).

## Tech Stack Decisions

- **Language:** TypeScript/Node.js LTS across all 10 backend services (house default; no Python — no AI/ML workload in scope).
- **Compute:** AWS Lambda, arm64, multi-stage Alpine Docker build where a container image is needed, zip for simple handlers — pay-per-invocation to meet the hard usage-based budget constraint.
- **Ingress:** API Gateway **HTTP API** (not REST API) + custom Lambda authorizer. Reconciles Moonaan's no-API-Gateway house ruling with requirements' hard AWS-serverless pin: API Gateway is used purely as TLS-termination/routing (no ALB option in pure-serverless topology); all JWT validation, rate limiting, and routing decisions stay in application code, never managed-gateway features.
- **Data:** DynamoDB, on-demand capacity, single-table design (3 physical tables — see above). PITR on all three. Table design assumes access-pattern-first modeling.
- **Search/reporting:** v1 uses purpose-built DynamoDB GSIs per access pattern. **OpenSearch/CQRS via OSI pipeline is explicitly deferred**, not rejected, on cost-floor grounds (AOSS has a standing cost floor disproportionate to this department's volume). DynamoDB Streams are on from day one on all three tables so OSI can be added later without a write-path change. Fast-follow trigger: a second department activating cross-department search, or incident/narrative-search volume outgrowing a GSI + FilterExpression.
- **Messaging — two distinct transports, deliberately:**
  - Alerting plane: **SNS FIFO topic `boxalarm-{env}-alerting-topic.fifo` → per-channel SQS FIFO queues + DLQs.** FIFO ordering + `MessageDeduplicationId` is load-bearing for exactly-once (N1.4). EventBridge has no FIFO mode and is never used for alerting fan-out.
  - Domain/LOB plane: **EventBridge bus `boxalarm-{env}-platform-bus`**, rule-routed to per-consumer SQS queues + DLQs. No ordering requirement on this plane.
  - **One-way bridge only:** a narrow allow-list of alerting events (`alerting.dispatch.received`, `alerting.response.confirmed`, `alerting.tone.escalated`, `alerting.mutual_aid.triggered`) republish outward from alerting to the LOB bus. Nothing on the LOB bus can reach back into the alerting plane.
  - EventBridge Scheduler is used within the alerting plane only for one-time escalation/tone-ladder timers — a scheduler, not a transport.
- **Orchestration:** Step Functions or EventBridge Scheduler one-time timers for the escalation ladder and NERIS submission retry/backoff — durable, observable state, not in-Lambda sleep loops.
- **Cache:** ElastiCache Serverless (Valkey) — config/reference data and reporting aggregations only, **never the alerting hot path** (cache is an explicit soft dependency; the alerting read path cannot tolerate "soft"). Cost floor (~$40-50/mo) flagged as disproportionate to LOB-plane volume — recorded as an open cost question, not resolved.
- **IaC:** Pulumi, dedicated `boxalarm-infrastructure` repo — the only repo touching AWS or holding Pulumi state.
- **Identity:** Amazon Cognito, single user pool per environment.
- **Authorization:** AWS Verified Permissions, Cedar policies encoding six roles (F2.7) and department scoping (F9.6/tenancy seam) as policy. `IsAuthorizedWithToken` per-request; `BatchIsAuthorizedWithToken` for list endpoints — never a per-item authorization loop. Fail-secure: a Verified Permissions outage returns 503, never a defaulted allow (except alerting-service's core fan-out/escalation pipeline, which has no per-request authz decision on the hot path).
- **Frontend:** React web SPA (no MFE — single team/release-train; revisit only if a second department needs independent deploy cadence) + React Native (New Architecture, bare workflow not Expo managed) for iOS/Android, sharing `@boxalarm/core`/`@boxalarm/design-tokens`/`@boxalarm/i18n` npm-workspace packages. UI components are NOT shared between web and RN.
- **No self-hosted broker** (no Kafka/RabbitMQ) — AWS-native only, pay-per-use, self-healing; a self-hosted broker is a fixed idle cost this department's "no 24/7 staffed support" constraint cannot absorb.

## Naming Conventions

- **Resource naming:** `boxalarm-{env}-*` everywhere. Any `moonaan-prod-*` name appearing anywhere in the document is template boilerplate and must be read as `boxalarm-{env}-*`.
- **Event naming:** lowercase dotted `<domain>.<entity>.<past-tense-verb>`, e.g. `alerting.dispatch.received`, `training.expiry.due`. PascalCase shorthand elsewhere in the document is non-canonical shorthand for this dotted form and must never appear in code/config/EventBridge rule patterns.
- **`domain` in an event name is always the owning service's short name** (not the triggering entity's domain) — e.g. `alerting.dispatch.received` (alerting-service owns dispatch ingress), `training.expiry.due` (training-service owns cert expiry), `inventory.expiry.due` (inventory-service owns PPE).
- **API base path:** `/api/v1/{service}/...`, JSON camelCase, RFC 7807 error envelope with `traceId`, contract-first OpenAPI per service. Exception: `notification-service` uses bare `/notifications/...` paths (predates the `/api/v1` convention and its own contract note is authoritative).
- **DynamoDB key format:** Moonaan convention `ENTITY_TYPE#value`, `pk`/`sk`/`gsiNpk`/`gsiNsk`. `{deptId}` is present in every table PK from day one (F9.6 tenancy seam), even with only one department in operation.
- **Exactly-once dedup key (canonical, amended):** `{dispatchId}#{toneSequence}#{memberId}#{channel}` — per-channel, per-tone. A key missing `toneSequence` or `channel` is a defect (silent-suppression class), never a valid implementation.
- **DynamoDB item shape for delivery receipts:** `sk = RECEIPT#{memberId}#{channel}#{toneSequence}`.
- **S3 prefix pattern:** `{deptId}/{entityType}/{entityId}/{filename}`.

## Cross-Cutting Non-Negotiables

- **Alerting is a separate failure domain from everything else (N1, N1.5, N1.7).** No component of `alerting-service` performs a synchronous read or write against the `platform-service` or `incident-service` tables, at fan-out time or ever — enforced as an **IAM boundary** (the alerting execution roles hold no IAM permission on the other two tables), not a convention. `platform-service`/`incident-service` outages must never degrade or block alert delivery.
- **Exactly-once delivery.** Two-layer idempotency: (1) transport-level SNS/SQS FIFO `MessageDeduplicationId = hash(dispatchId, toneSequence, memberId, channel)` (cost-free first filter, never the enforced guarantee — its 5-min window doesn't cover all redelivery); (2) application-level DynamoDB conditional put on `idempotencyKey = {dispatchId}#{toneSequence}#{memberId}#{channel}`, `attribute_not_exists` guard, performed in the channel worker immediately before the provider send call — this is the actual enforced invariant. **`channelTier` (`primary`|`escalation`) is escalation-state bookkeeping ONLY — never a routing filter, never a dedup input.** Routing and dedup both key on `channel`. `BatchWriteItem` is forbidden for any guarded write (cannot carry a `ConditionExpression`) — use `TransactWriteItems` or per-item `PutItem`.
- **Escalation ladder (decided, canonical):** push + SMS fire in parallel at T+0 (both `channelTier=primary`); voice is the sole escalation tier, firing at T+N (default 75s, F9.3-configurable) only if neither push nor SMS is acknowledged. This is the correct reading of N1.2 (independent failure domains) — a sequential ladder would make every push failure cost a full escalation interval before SMS attempts.
- **Department-level tone ladder (F1.12-F1.14, amendment), orthogonal to per-member escalation.** Two additional dept-level EventBridge Scheduler one-time schedules fire at T+180s (tone 2) and T+360s (tone 3, both F9.3-configurable), each carrying a **literal, immutable `toneSequence` fixed at schedule-creation time — never computed at fire time** (EventBridge Scheduler is at-least-once; computing "current+1" at fire time would let a redelivered invocation mint a tone early). Audience for each tone is the **full current eligible-member set re-resolved fresh, never filtered by `ackStatus`** — a member who answered `NOT_RESPONDING` or `RESPONDING` is by default still re-toned (`ALERT_RULES.retoneRespondingMembers` default `true`). Voice re-arms on every tone by default (`ALERT_RULES.voiceEscalatesPerTone` default `true` — up to 3 voice attempts/dispatch for a never-acking member). Officer-overridable: halt (`POST .../tone-ladder/halt`) and advance (`POST .../tone-ladder/advance`) via idempotent, conditionally-guarded writes — no schedule cancellation is ever used, only self-check-and-skip at fire time.
- **Mutual aid (F1.13) is a port, not an inter-department API.** The shipped default adapter notifies our own officers/chief (`alertKind: "mutual_aid_prompt"`, `MAPROMPT#{memberId}#PUSH` item namespace, distinct from `RECEIPT#...`) and records `MUTUAL_AID_EVENT` (singleton per dispatch, conditional put) pending a human phone call. A CAD-relay adapter to a neighboring department is a named future variant, not designed, gated on OQ-1/OQ-2.
- **Event envelope (standard, required on every event):** `eventId` (UUID, dedup key), `eventTime` (ISO-8601, producer-assigned), `eventType` (`{domain}.{entity}.{verb}`, past tense), `source` (emitting service), `correlationId` (threads a business transaction — for alerting this is `dispatchId`), `schemaVersion` (semver), `payload` (domain-specific object).
- **Error envelope:** RFC 7807 (`application/problem+json`), every response carries `traceId` (W3C `traceparent`/`tracestate` propagated on every inter-service call).
- **Auth model:** Amazon Cognito is the sole identity provider (OAuth2 Authorization Code + PKCE on mobile, no client secret in the binary). One Lambda authorizer in front of API Gateway does all 4 JWT checks (signature/JWKS, audience via `client_id` on access tokens, issuer, expiration) via `aws-jwt-verify`. Authorization via AWS Verified Permissions/Cedar. Vendor webhooks (CAD ingress, delivery receipts) authenticate by vendor-specific signature/shared secret, never Cognito.
- **NO MFA, NO step-up re-authentication, NO session timeout, anywhere (N5.2) — this is deliberate and canonical, not an oversight.** `MfaConfiguration: OFF`; access/ID token validity 1 hour; **refresh token validity 3650 days** (Cognito ceiling) on both native and web, no asymmetry; silent background refresh so first sign-in is the only interactive one; refresh-token rotation with a grace window. `POST /platform/export` and destructive admin actions are gated by a **Cedar chief/admin role check alone**, no re-prompt. **Revocation is the only control that replaces expiry** — Cognito global sign-out / refresh-token revocation on member status change (LOA, retired), per-device revocation from the admin console, invocation alarms on export. A login prompt or MFA challenge anywhere on the alert path is an **alerting failure (N1)**, not a hardening improvement, and a test failure if one appears. See OQ-24 (who revokes a compromised session, and how fast) — the only open control gap this leaves.
- **Observability:** structured JSON logs (stdout) carrying `correlationId`+`service`; AWS X-Ray active tracing on every Lambda, correlated per `{dispatchId}#{toneSequence}#{memberId}#{channel}`. X-Ray is a diagnostic aid only (days retention) — the durable audit record is the immutable `DELIVERY_RECEIPT` items archived to S3 Object Lock. CloudWatch alarms for alerting (fan-out p99 vs 5s N1.1 target, per-channel delivery-failure rate, canary failure, duplicate-delivery counter, `ToneFiredZeroReceipts`) are **P0, page-immediately**, never folded into a general dashboard. No PII in logs.
- **Deployment (N2.2):** no maintenance window ever for `alerting-service` — every Lambda deploys via a versioned alias with CodeDeploy canary/linear traffic shift, gated by the N1.6 canary running clean against the new version and the same CloudWatch alarms that page on-call also serving as automatic rollback triggers.
- **Data residency:** all resources pinned to a single U.S. region (`us-east-1`) — a NERIS vendor obligation (N6.1), not a preference.
- **No PHI anywhere** — fire-only scope, EMS/ePCR explicitly excluded; this is what keeps HIPAA/BAA/NEMSIS out of the design entirely.
- **Tenancy seam:** `{deptId}` present in every table PK from day one (F9.6) — single department in operation, multi-tenant seam only, additive not a rewrite if a second department is added.
- **Retention:** life-safety audit evidence (`DELIVERY_RECEIPT`, `ESCALATION_EVENT`, `DISPATCH_ALERT`, `DISPATCH_RESPONSE_RECORD`, `TONE_EVENT`, `MUTUAL_AID_EVENT`) has **no TTL-based deletion** — governed by a separate scheduled export-to-S3-Glacier job (default 7 years, N6.3-configurable), never silent timer expiry.

## Open Questions

- **OQ-1 (blocking).** CAD/dispatch ingress mechanism — no vendor, protocol, or confirmed digital feed exists. `DispatchIngressPort` abstraction designed against this; no adapter can be built until resolved. Owner: fire chief + platform operator, needed immediately.
- **OQ-2 (blocking, longest pole).** Regional dispatch authority approval for CAD integration. Owner: fire chief, start this week.
- **OQ-3.** SMS and voice vendor selection, unconfirmed — must be two distinct commercial vendors (N1.2 independent-failure-domain requirement), plus data-handling terms (no content retention beyond delivery confirmation, U.S.-only processing). Owner: platform operator, Wave 1.
- **OQ-4.** Apple Critical Alerts entitlement — who applies and when is unresolved; architecture assumes it is obtained before N1 is fully met, with N1.8 degraded-mode fallback documented for the interim. Owner: platform operator, start this week.
- **OQ-5 (resolved).** Mobile OIDC library — `react-native-app-auth` (AppAuth, system-browser PKCE) ratified; the credible-alternative set is empty.
- **OQ-8.** Canary cadence (proposed every 1-2 min) — not specified in requirements, trades detection speed against provider cost.
- **OQ-9.** API Gateway standards deviation (house ruling forbids it; requirements pin it) — reconciled as TLS-termination/routing only, app code owns JWT/rate-limiting/routing logic; needs explicit ratification as acceptable rather than an unratified deviation.
- **OQ-10–OQ-14.** Station alerting hardware preservation, Chief360 data migration scope/format, CT LOSAP statutory point rules, CT state fire reporting beyond NERIS, mutual aid / cross-department visibility — all unresolved, all modeled generically/deferred pending answers, owner department admin, backlog refinement.
- **OQ-18.** Who carries the pager — who is woken at 03:00 when the canary detects a broken alert path, and by what, given no 24/7 staffed support exists. The most consequential unanswered question in the document. Owner: fire chief + platform operator, before Wave 1 ships.
- **OQ-19.** CT/municipal records-retention schedule — the 7-year default was a considered guess, not a requirement.
- **OQ-20.** Mapping provider — unselected, needed for F1.8 map link and F6.6 map retrieval.
- **OQ-21.** Who operates the platform day to day and against what monthly cost ceiling — budget is invoked as a hard constraint driving at least 4 architectural decisions (no OpenSearch, no Kafka, HTTP API, on-demand DynamoDB) with no figure or owner attached. Rough estimate: **$120-175/month total** (AWS ~$60-80, SMS/voice ~$60-95), dominated by the unresolved Valkey cost-floor question and vendor-dependent SMS/voice rates.
- **OQ-22.** Members without a capable smartphone — a real coverage gap under the eventual N1.9 tone-out cutover; policy decision, not technical. Owner: fire chief, before N1.9 cutover.
- **OQ-23.** NERIS Integration Partner vendor account provisioning — lead time unknown, blocks any production NERIS submission.
- **OQ-24.** Who revokes a compromised/lost session, and how fast — with MFA, step-up, and session expiry all removed by product decision, revocation is the only remaining control, and OQ-18/OQ-21 establish no staffed human exists to exercise it. Owner: fire chief + platform operator, before Wave 1 ships.
- **OQ-25.** Who is authorized to halt the tone ladder, and does a halt require second-officer concurrence — department SOG question, not an engineering one. Owner: fire chief, before Wave 1 ships F1.14.
- **[ASSUMED]** Chief360 export scope/format unknown — migration strategy (backfill, not lazy/dual-write) is provisional pending this answer; no incident data migrates (Chief360 is not NERIS-native).
- **[ASSUMED]** Single NERIS `dispatchId`/`incidentId` is minted once at alert ingestion and reused unchanged as the `INCIDENT` key — the linkage that lets `alerting-service`/`incident-service` correlate without a shared table. Revisit if NERIS or the eventual CAD integration mints the number later in the workflow.
- **Assumption, stated:** "independent vendor" for SMS/voice means two different commercial providers from each other and from push's Apple/Google dependency — not that shared AWS-native substrate (Lambda, SQS, EventBridge) itself must be avoided.
